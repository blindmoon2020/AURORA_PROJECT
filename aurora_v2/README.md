## Verify it yourself in ten minutes

No dependencies. Python 3.10+ and the standard library.

```bash
git clone -b aurora-v2 https://github.com/blindmoon2020/AURORA_PROJECT.git
cd AURORA_PROJECT/aurora_v2

python -m unittest discover -s tests -t . -v      # 64 tests
python scripts/run_backtest.py --data synthetic --candles 5000 --seed 7
python scripts/research.py --symbol EURUSD=X --interval 1d --range 10y --folds 4
```

The last command re-fetches the data, reruns 81 configurations, the walk-forward,
the overfitting checks, and rewrites `docs/RESEARCH_DAILY.md`. If a number in this
README disagrees with that output, the script is right and the README is stale.

## Results

Walk-forward only: parameters chosen on the past, traded on the block after it,
8-bar embargo, 0.2 pip spread, 0.1 pip stop slippage, next-bar-open fills.

| | EURUSD 1h / 2 years | EURUSD 1d / 10 years |
| --- | --- | --- |
| out-of-sample trades | 115 | 25 |
| profit factor | 1.11 | 0.42 |
| net P&L on 10,000 | +408.13 | −557.56 |
| Sharpe / max drawdown | 0.36 / 6.86% | −0.63 / 7.85% |
| p-value | 0.579 | 0.071 |
| PBO (probability of backtest overfitting) | 0.27 | 0.50 |
| deflated Sharpe | 0.000 | 0.000 |
| in-sample best of 81 configs | Sharpe 1.52 | Sharpe 0.66 |

The in-sample winner looks like a strategy. One block later, with parameters
chosen only on prior data, it is a coin flip. **MinBTL** explains why: 81 trials
at a target Sharpe of 1.0 need about 6 years of data; the hourly series has 2.8.

## Architecture

```
data ──► strategies ──► risk ──► execution ──► journal ──► metrics
 │            │           │          │            │           │
 │            └─ proposal └─ veto    └─ fill    └─ reason  └─ validation
 └─ candles, provenance, cleanliness report
```

| Module | Responsibility | Key file |
| --- | --- | --- |
| `aurora/core` | candle types, event bus, event definitions | `events.py` |
| `aurora/strategies` | strategy protocol, one-pass EMA cross, DNA (JSON) loader | `dna.py` |
| `aurora/risk` | sizing from account risk, daily and total limits, kill switch | `engine.py` |
| `aurora/execution` | broker protocol and paper broker (spread, slippage, gaps) | `paper.py` |
| `aurora/journal` | append-only decision log, ids linking trade to decision | `decision_log.py` |
| `aurora/backtest` | runner and metrics (realized and mark-to-market curves) | `runner.py` |
| `aurora/validation` | walk-forward with embargo, PBO by CSCV | `walkforward.py`, `pbo.py` |
| `aurora/data` | synthetic fixture, CSV adapter, Yahoo fetcher, cleaning | `validate.py` |
| `aurora/stats.py` | Sharpe, Sortino, Calmar, t-test, PSR, DSR, MinBTL | — |

Design rules, enforced by tests: a strategy never sizes a position, risk never
places an order, execution never invents a price, and no trade exists without a
decision record.

## Execution model — the part that decides the result

- a signal is generated on the close of bar *i*; the order fills at the **open of bar *i+1***
- entry pays half the spread, exit pays the other half
- a bar that gaps through the stop fills **at the open**, not at the stop
- stop fills take adverse slippage; target fills do not
- a bar touching both stop and target closes at the **stop**
- commissions are charged on both legs and sit inside trade pnl
- `final_equity == starting_balance + sum(trade.pnl)` is asserted by a test

## Risk rules, in the order they are checked

1. kill switch active → nothing trades until a human resets it
2. total drawdown cap → the switch trips itself
3. stop on the losing side of entry → rejected
4. daily loss cap reached → done for the day
5. daily trade cap → churn is a cost centre
6. max open positions / one position per symbol
7. notional above `equity × max_leverage`
8. size rounds to zero

`units = equity × risk_per_trade_pct / |entry − stop|`. There is no fixed lot
anywhere in the codebase, and every rejection is written into the decision log
with its reason.

## Validation methodology

| Tool | What it prevents |
| --- | --- |
| walk-forward with 8-bar embargo | choosing parameters with hindsight, and leaking open positions across the boundary |
| CSCV probability of backtest overfitting | mistaking a lucky parameter for a good one (published rejection level 0.05; our working ceiling 0.10) |
| deflated Sharpe (Bailey & López de Prado) | ignoring how many configurations were tried |
| PSR, t-statistic, confidence interval | reporting a mean return that cannot be distinguished from zero |
| MinBTL | searching 81 configurations on 2.8 years of data, which cannot prove anything |
| trade-level review | accepting a result nobody has looked through |

## Run it on your own data

```bash
python scripts/run_backtest.py --data csv --csv path/to/EURUSD_M5.csv \
    --dna strategies/ema_cross_eurusd.json --out runs/eurusd/decisions.jsonl
```

The CSV adapter accepts `ts,open,high,low,close[,volume]` with common header
aliases and epoch or ISO timestamps.

## Add a strategy without touching the engine

Write a JSON DNA file: type, parameters, risk limits. The loader validates it,
`DnaError` explains exactly what is wrong, and the same walk-forward machinery
applies without code changes. That is the "strategy as data" idea AURORA always
claimed and did not have.

## Roadmap, in order, no skipping

1. swap/financing in the cost model, then a portfolio layer with correlation-aware exposure
2. a premise with an economic reason (carry, session liquidity, volatility premium), pre-registered before touching data
3. multi-symbol, 10+ year walk-forward with the trial count declared up front
4. paper execution with an order state machine and measured TCA
5. small live capital only after V1 and V2 both clear

## What is deliberately not here

No multi-agent "AI council", no self-improving architecture, no microservices, no
dashboard, no cloud. Each would add surface area without adding expectancy. The
conditions for revisiting any of them are written down in the vision document.

## For a buyer or investor

What you can verify today: the code, the tests, the two research reports, and the
fact that the system reports "no edge" about its own strategy. What does not exist
yet: a track record, live execution, measured transaction costs. Anyone pricing
this as a profitable bot today is pricing something that is not in the repository.

## Requirements and contribution

Python 3.10+. No runtime dependencies, by design: `requirements.txt` is empty and
the measured core must stay reproducible. Tests use stdlib `unittest`; CI runs them
on 3.10, 3.11 and 3.12. Architecture changes to `core`, `risk` or `execution` need
a short ADR: decision, alternatives, effect on results, rollback.

## Disclaimer

Research software. Nothing here is investment advice, and the measured results
